## Architecture

The project implements a three-layer architecture that mirrors SAP GUI's internal model. Layer B is the source of truth — Layer A renders it, Layer C exposes it to scripts.

### Layer A — Visual Shell (`main.py`, `ui/`)
The Qt/PySide6 front-end. `MainWindow` builds the classic-style window chrome. `TransactionRouter` renders the `Navigator`'s sessions. Scripts can arrive on other threads, so navigation and widget updates go through `ui/gui_thread.py`. `ScreenRenderer` maps engine controls to Qt widgets via `WidgetFactory`. `app.setStyle("Fusion")` is required. Toolbars are re-parented into a `QVBoxLayout` to force correct stacking order.

### Layer B — Control Tree Engine (`engine/`)
30+ control classes in `engine/control.py` (base `Control` with subclasses: `Container`, `TextField`, `ComboTextField`, `Button`, `GridView`, `TableControl`, `Tree`, etc.). `Session` in `engine/session.py` provides `findById()` with O(1) registry lookup. `engine/loader.py` reconstructs a `Session` from captured screen JSON files in `screens/`. `engine/navigation.py` holds `Navigator`, which owns the transaction flows: it loads screens and wires buttons, virtual keys, and the command field, so every bridge and the UI share one behaviour. Listeners are told about each new session. `engine/transactions/` has hand-authored screens (`SE16InitialScreen`, `SessionManagerScreen`, etc.).

### Layer C — Scripting Bridge (`bridge/`)
Three mechanisms, all operating on the same engine Session:
1. **In-process Python** (`bridge/proxy.py`): `SandboxSession` / `ControlProxy` — PascalCase and snake_case.
2. **HTTP JSON API** (`bridge/server.py`, `bridge/client.py`): `SandboxServer` / `RemoteSession` on localhost.
3. **COM/ROT** (`bridge/com_server.py`, `bridge/com_thread.py`): 7 COM wrapper classes registered in the Windows Running Object Table via `CreateFileMoniker("SAPGUI")`. STA thread with `MsgWaitForMultipleObjects` message pump. `_value_` method on `ComCollection` handles DISPID_VALUE dispatch for `coll(i)` syntax.

## Screen JSON Files

`screens/` contains 18 English sample screens with fictional data, all generated by `tools/generate_screens.py`; edit that script rather than the JSON. Never commit captures or screenshots of a live system; `tests/test_screens_sanitized.py` guards part of this. Each file has metadata (`system`, `client`, `user`, `transaction`, `screen_number`) and a recursive control tree. `engine/loader.py` uses `_TYPE_MAP` to instantiate the correct Python class for each node.

## SAP Logon Pad and Environments

`main.py` opens on the SAP Logon pad (`ui/logon_pad.py`), which lists the environments in `environments.json` (loaded and validated by `engine/environments.py`). `WL` opens on the logon screen, `NL` on Easy Access. Opening one calls `MainWindow.open_environment()` → `Navigator.connect(env)`; one connection at a time, and closing the session window calls `disconnect()` and returns to the pad. `python main.py --env WL|NL` skips the pad (`--no-logon` = `--env NL`). Over COM there is no connection until one is opened: `GuiApplication.OpenConnection(description_or_id, True)` opens it on the GUI thread through the `opener` passed to `ComBridge`.

## Logon Screen

The `WL` environment opens on the logon screen (`00_LOGON.json`, transaction `S000`). `MainWindow()` defaults to `require_logon=False` so tests start on Easy Access. The logon state lives in `Navigator` (`engine/navigation.py`), so the window and every bridge share it. While logged off, it blocks every transaction; Enter (VKey 0) on the logon window calls `attempt_logon()`, and `/nend` or `/nex` logs off. Test users live in `users.json`, keyed by environment id (`engine/users.py`, `UserStore`); changes are kept in memory and never written back. Scripts send Enter from the COM/HTTP thread, so the logon runs on the GUI thread through `ui/gui_thread.py` and the call blocks until the next screen is shown.

## Popups and Password Workflows

Modal popups are `ModalWindow` (`GuiModalWindow`) windows built at runtime by `engine/popups.py` and added to the session as `wnd[1]` (`wnd[2]` for an information message). The Navigator wires Enter/`btn[0]` to continue and F12/`btn[12]` to cancel, and ignores the windows below while one is open; `ui/popup_dialog.py` shows each as a non-blocking Qt dialog (`open()`, never `exec()`). Password flows: Set (logon `tbar[1]/btn[5]`), Forced (initial password at logon), SU3 (`tbar[1]/btn[6]`, fields under `usr/subSUBSCREEN:SAPMSYST:0043`), Reset (SU01 `tbar[1]/btn[20]`). A rejected password opens `wnd[2]`. The IDs match PySapGUI's `saplogonpwd.py`; `tests/test_pysapgui.py` runs that library against the sandbox (test-only dependency, GPL-2.0, never imported by the app). Status bars carry `MessageNumber` (`343` unknown transaction, `190` password can't be changed).

## Reactive Flows

A reactive flow checks the input before moving on and fills the next screen with matching data, instead of always showing the same next screen. Base class and registry: `engine/reactive.py` (`ReactiveFlow`, `REACTIVE_FLOWS`). The Navigator calls `check()` in `_next` (an error stays on the screen with a status bar message) and `fill()` in `_show` (also on Back, so typed values come back). `XD03` (`engine/customers.py`) looks customers up in `customers.json` (fictional; leading zeros ignored, optional company code). Its screens come from `tools/generate_reactive_screens.py`, which `tools/generate_screens.py` includes. A new flow: subclass `ReactiveFlow`, call `register()`, import the module in `engine/navigation.py`, and add its screens to `reactive_screens()`.

## Key Conventions

- **Widget objectNames = automation IDs.** Every Qt widget gets `setObjectName()` matching the SAP-like path.
- **SAP ID format:** `wnd[N]/area/controlId` — `wnd[0]` is main window, `usr` is user area, `tbar[0]` is main toolbar.
- **COM moniker:** `"SAPGUI"` (same as real SAP).
- **Count is a property**, not a method — `children.Count` not `children.Count()`.

## Test Suite

- `tests/test_engine.py` — Control tree, Session, findById, load_screen, transactions
- `tests/test_ui.py` — Qt widget rendering, ScreenRenderer, TransactionRouter
- `tests/test_e2e.py` — Full stack: load screen → render → interact → verify
- `tests/test_navigation.py` — Script-driven navigation through the engine, bridges, and live window
- `tests/test_logon.py` — Logon screen (S000): rules in `engine/logon.py`, UI flow, logon from a script thread
- `tests/test_environments.py` — Environment list, `Navigator.connect`, the SAP Logon pad, `OpenConnection`
- `tests/test_passwords.py` — `users.json`, password rules, the Set/Forced/SU3/Reset popups and their Qt dialog
- `tests/test_pysapgui.py` — PySapGUI's password helpers run against the sandbox (skipped if PySapGUI isn't installed)
- `tests/test_customers.py` — XD03 reactive flow: lookup rules, Navigator flow, live window, script thread
- `tests/test_com_collections.py` — COM collections indexed the way VBScript does it (`obj.Children(0)` in one call)
- `tests/test_com_bridge.py` — Manual COM smoke test; run as a script while `main.py` is running
- `tests/test_screens_sanitized.py` — Rejects screen files holding live-system identifiers
- `tests/conftest.py` — Shared fixtures: `qapp` (session-scoped QApplication), `main_window`
