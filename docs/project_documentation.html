GUI Sandbox

A three-layer desktop application that emulates the SAP GUI for RPA development, test automation, and training — no live SAP connection required.

1. Why This Exists

SAP GUI Scripting (the COM-based automation API built into SAP’s Windows client) is the backbone of most SAP RPA projects. But developing and testing those scripts has a hard dependency: a live SAP system, a valid login, and a connection to the right client. That means scripts can’t be developed offline, tested in CI, or safely debugged without touching real data.

This sandbox removes that dependency. It rebuilds a SAP-style control tree from JSON screen files — every field ID, every button, every table cell — and exposes it through the same COM interface that real SAP uses. The result:

  • Develop RPA scripts against realistic SAP screens without a live connection.
  • Replay sample screens — the sandbox loads fictional JSON screen files.
  • Drop-in compatibility — change one line (GetObject("SAPGUI") instead of GetObject("SAPGUI")) and existing scripts run against the sandbox.
  • Action recording — every findById, setText, press, sendVKey is logged with timestamps for test validation.

2. Architecture Overview

The project mirrors SAP GUI’s own internal architecture with three distinct layers. Each layer is independently useful and has no upward dependencies:

┌─────────────────────────────────────────────────────────────────┐
│  External Scripts  (Python, VBScript, UiPath, etc.)             │
│                                                                 │
│  sap = GetObject("SAPGUI")                               │
│  session = sap.GetScriptingEngine.Children(0).Children(0)       │
│  session.findById("wnd[0]/usr/ctxtFOO").Text = "SFLIGHT"           │
└──────────────────────────┬──────────────────────────────────────┘
                           │
          ┌────────────────▼────────────────┐
          │     Layer C: Scripting Bridge    │
          │                                 │
          │  COM/ROT ─ HTTP API ─ In-Proc   │
          │  bridge/                        │
          └────────────────┬────────────────┘
                           │  delegates to
          ┌────────────────▼────────────────┐
          │   Layer B: Control Tree Engine   │
          │                                 │
          │  Session ─ Window ─ Controls    │
          │  findById() ─ O(1) registry     │
          │  engine/                        │
          └────────────────┬────────────────┘
                           │  renders
          ┌────────────────▼────────────────┐
          │     Layer A: Visual Shell        │
          │                                 │
          │  PySide6/Qt ─ classic-style UI     │
          │  main.py                        │
          └─────────────────────────────────┘

Key design principle: Layer B is the source of truth. Layer A renders it visually. Layer C exposes it to external scripts. All three operate on the same in-memory control tree.

LAYER A

3. Visual Shell

The Qt/PySide6 front-end renders the classic-style window chrome. It is implemented entirely in main.py.

What it builds

MainWindow(QMainWindow) assembles six stacked horizontal zones, matching the real SAP GUI layout top to bottom:

┌─────────────────────────────────────────────┐
│  Menu Bar     Menu │ Traiter │ Favoris │ ...  │
├─────────────────────────────────────────────┤
│  Main Toolbar  ✓  [command field ▼]  Save Back │
├─────────────────────────────────────────────┤
│  Title Banner  GUI Sandbox - User Menu       │  gradient
├─────────────────────────────────────────────┤
│  Context Toolbar  Open │ Create │ Delete │..│
├─────────────┬───────────────────────────────┤
│  Nav Tree    │  Workspace Panel               │
│  📁 Favoris │                               │
│  📁 Menu    │        (content area)         │
│             │                               │
├─────────────┴───────────────────────────────┤
│  Status Bar   Ready                          │
└─────────────────────────────────────────────┘

Implementation details

  • app.setStyle("Fusion") is called before showing the window — this is required for the SAP color palette to render correctly.
  • Toolbars are removed from Qt’s native toolbar system and re-parented into a QVBoxLayout to force the correct stacking order. Without this, Qt may reorder toolbars or allow the user to drag them.
  • Every widget gets a stable objectName matching SAP-like IDs (e.g. cmd_field, btn_save, nav_tree).

LAYER B

4. Control Tree Engine

The core data model. Every UI element in a SAP screen is represented as a Python object in a tree, independent of any UI framework. This is what makes automation possible.

Control class hierarchy

All classes live in engine/control.py. The base Control class holds the properties every SAP element has. Each subclass sets a sap_type class attribute that matches the real SAP GUI Scripting COM type name:

Session & Window

Defined in engine/session.py. Session is the top-level object (mirrors GuiSession in SAP COM).

session = load_screen("screens/02_SE16_initial.json")

# O(1) lookup via internal registry (dict[str, Control])
field = session.findById("wnd[0]/usr/ctxtDATABROWSE-TABLENAME")
field.value = "SFLIGHT"

# Accepts both full and short paths
session.findById("/app/con[0]/ses[0]/wnd[0]/usr/ctxtFOO")   # full
session.findById("wnd[0]/usr/ctxtFOO")                       # short

# VKeys, transactions, status bar
session.send_vkey(0)                   # Enter
session.start_transaction("SE16")
session.set_status("Saved.", "S")

SessionInfo holds read-only metadata: system_name, client, user, transaction, program, screen_number.

JSON loader

engine/loader.py reconstructs a full Session from a screen JSON file. It uses _TYPE_MAP (30+ entries mapping SAP COM type strings to Python classes) to instantiate the correct control type for each node. Special handling for TableControl (pre-parsed rows), GridView (rows as dicts), and selection state on RadioButton/CheckBox/Tab.

from engine import load_screen, build_tree

# From a file
session = load_screen("screens/02_SE16_initial.json")

# From a pre-parsed dict (e.g. from an HTTP API)
session = build_tree(json_data)

Transaction screens

engine/transactions/ contains hand-authored screen classes that build control trees programmatically (without a JSON file):

LAYER C

5. Scripting Bridge

Three complementary mechanisms expose the control tree to external automation scripts. All three share the same ActionRecorder for logging.

Mechanism 1: In-process Python proxy

Wrap any Session in a SandboxSession for a SAP COM-compatible Python API. Both PascalCase (.Text) and snake_case (.text) are supported.

from bridge import SandboxSession
from engine import load_screen

session = SandboxSession(load_screen("screens/02_SE16_initial.json"))

# Exact SAP GUI Scripting syntax
session.findById("wnd[0]/usr/ctxtDATABROWSE-TABLENAME").Text = "SFLIGHT"
session.findById("wnd[0]").sendVKey(0)
print(session.Info.Transaction)       # "SE16"
print(session.recorder.entries())     # action log

Mechanism 2: HTTP JSON API

For cross-process / cross-language access (UiPath, test harnesses, browser tools).

# === Server side ===
from bridge import start_server
from engine import load_screen
server = start_server(load_screen("screens/02_SE16_initial.json"), port=7654)

# === Client side (any language) ===
from bridge import RemoteSession
session = RemoteSession("http://127.0.0.1:7654")
session.findById("wnd[0]/usr/ctxtDATABROWSE-TABLENAME").Text = "SFLIGHT"
EndpointMethodDescription
/infoGETSession metadata (transaction, user, screen)
/treeGETFull control tree as nested JSON
/controlsGETFlat list of all controls
/logGETAction recorder entries
/findByIdPOST{"path": "wnd[0]/usr/ctxtFOO"}
/actionPOST{"path": "...", "action": "setText", "value": "X"}
/loadScreenPOST{"file": "screens/02_SE16_initial.json"}

Mechanism 3: Windows COM / ROT

The flagship mechanism. A background STA thread registers COM objects in the Windows Running Object Table (ROT), so external scripts connect via GetObject("SAPGUI") — exactly how real SAP works, just with a different moniker name.

GetObject("SAPGUI")
  │
  ├── .GetScriptingEngine  →  ComApplication
  │     └── .Children(0)   →  ComConnection
  │           └── .Children(0)  →  ComSession
  │                 ├── .findById(path)  →  ComControl
  │                 │     ├── .Text  (read/write)
  │                 │     ├── .Press()
  │                 │     ├── .sendVKey(key)
  │                 │     ├── .Children  →  ComCollection
  │                 │     └── .Id, .Type, .Name, .Enabled, ...
  │                 ├── .Info  →  ComSessionInfo
  │                 │     └── .Transaction, .User, .SystemName, ...
  │                 ├── .ActiveWindow  →  ComControl
  │                 └── .sendVKey(key)

How it works internally

  1. ComBridge.start() spawns a daemon thread that calls pythoncom.CoInitialize() (STA apartment).
  2. It creates a ComSapGui instance wrapping the engine Session, wraps it with win32com.server.util.wrap(), and registers it in the ROT via pythoncom.CreateFileMoniker("SAPGUI").
  3. The thread enters a message pump loop (PumpWaitingMessages() every 50ms) so incoming COM calls from external processes are dispatched.
  4. On shutdown, the thread revokes from the ROT and calls CoUninitialize().

Drop-in compatibility

Existing SAP automation scripts need exactly one change:

# Before (real SAP):
sap = win32com.client.GetObject("SAPGUI")

# After (sandbox):
sap = win32com.client.GetObject("SAPGUI")

# Everything below is unchanged
app = sap.GetScriptingEngine
session = app.Children(0).Children(0)
session.findById("wnd[0]/usr/ctxtFOO").Text = "1000"
session.findById("wnd[0]").sendVKey(0)

Action Recorder

bridge/recorder.py provides an append-only log shared by all three mechanisms. Every scripting operation is recorded with a UTC ISO-8601 timestamp, the action name, the target control path, and any value written or returned.

recorder.log("setText", path="wnd[0]/usr/ctxtFOO", value="SFLIGHT")
recorder.save("session_log.json")    # persist to file
recorder.entries()                   # list of dicts
recorder.filter("sendVKey")          # filter by action

6. Tools & Screen Capture Pipeline

The tools/ directory contains scripts that connect to a real SAP GUI session, walk the live control tree, and export it as JSON. These JSON files are what the sandbox loads and replays.

Real SAP GUI  ──→  tools/sap_inspect.py  ──→  screens/*.json  ──→  engine/loader.py  ──→  Session
(live COM)          (walks control tree)        (JSON snapshots)     (reconstructs tree)    (in-memory)
ScriptPurpose
sap_connect.pyCore connection module. get_session() attaches to a running SAP GUI via GetObject("SAPGUI"). launch_and_login() opens SAP Logon and fills the login screen programmatically.
sap_inspect.pyWalks the full control tree of the active SAP screen and exports it as JSON. Extracts all properties, table data, grid columns/rows.
sap_scenarios.pyAutomated multi-screen capture. Navigates through transactions (SE16, SU01, SM37, etc.), captures each screen to screens/, generates _manifest.json.
sap_launch.pyLaunches SAP Logon, waits for login, then optionally runs the inspector or scenarios.
generate_screens.pyGenerates the sample screens in screens/.

CLI entry point

run_sandbox.bat dispatches to the tools using the system Python (which has pywin32 for COM):

run_sandbox.bat launch              # start SAP, wait for login
run_sandbox.bat inspect             # capture current screen to JSON
run_sandbox.bat inspect --out screens/myscreen.json
run_sandbox.bat scenarios all       # run all capture scenarios
run_sandbox.bat scenarios SE16 --table MARA

8. Usage Guide

Quick start

# Install dependencies
pip install -r requirements.txt

# Launch the sandbox (starts Qt UI + COM bridge)
python main.py

The app loads screens/02_SE16_initial.json by default and registers GetObject("SAPGUI") in the ROT. You’ll see COM bridge started in the terminal.

Connect from a Python script

import win32com.client

sap = win32com.client.GetObject("SAPGUI")
app = sap.GetScriptingEngine
session = app.Children.Item(0).Children.Item(0)

# Read a field
field = session.findById("wnd[0]/usr/ctxtDATABROWSE-TABLENAME")
print(field.Text)              # ""

# Write a field
field.Text = "SFLIGHT"
print(field.Text)              # "SFLIGHT"

# Press Enter
session.findById("wnd[0]").sendVKey(0)

# Read session info
print(session.Info.Transaction)  # "SE16"
print(session.Info.User)         # "USER_STANDARD"

Connect from VBScript

Set sap = GetObject("SAPGUI")
Set app = sap.GetScriptingEngine
Set session = app.Children(0).Children(0)
session.findById("wnd[0]/usr/ctxtDATABROWSE-TABLENAME").Text = "SFLIGHT"
session.findById("wnd[0]").sendVKey 0
MsgBox session.Info.Transaction

Use the HTTP API instead

from bridge import start_server
from engine import load_screen

server = start_server(load_screen("screens/02_SE16_initial.json"), port=7654)
# Then from any HTTP client:
# POST http://127.0.0.1:7654/findById  {"path": "wnd[0]/usr/ctxtDATABROWSE-TABLENAME"}
# POST http://127.0.0.1:7654/action    {"path": "...", "action": "setText", "value": "SFLIGHT"}

Use in-process (same Python script)

from bridge import SandboxSession
from engine import load_screen

session = SandboxSession(load_screen("screens/04_SE16_SFLIGHT_results.json"))
grid = session.findById("wnd[0]/usr/cntlGRID1/shellcont/shell")
print(grid.RowCount)
print(grid.GetCellValue(0, "CARRID"))

Capture new screens from a live SAP

run_sandbox.bat launch              # opens SAP Logon, waits for login
run_sandbox.bat inspect --out screens/my_screen.json
run_sandbox.bat scenarios all       # automated multi-screen capture
